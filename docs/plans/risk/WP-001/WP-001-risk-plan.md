# Risk Plan: SPEC-001 Database and Schema Implementation

Work Plan ID: WP-001
Created Date: 2026-08-13

## Context

This risk plan covers the execution of `docs/plans/2026-08-13-WP-001.md` (13 tasks,
4 phases) implementing SPEC-001. Established context that is *not* re-litigated here
(it is input, not risk): the repository is greenfield on `feature/v2` so every source
file is new; the migration CI job and any provisioned PostgreSQL instance are waived by
binding user decision, so AC-1 … AC-10 are implemented-but-unverified and only AC-11 is
closable; unit tests exist for the seeding component only; `[PG-005]` and `[PG-014]`
waivers are user-approved; both images pin Python 3.14 for stdlib `uuid.uuid7()`.

The risk posture that follows from that context, and which this plan concentrates on:

1. **Nothing in this changeset ever touches a real database.** Every defect class that
   only manifests at DDL execution or transaction time ships undetected. The only
   defences available are static (offline SQL render, review, mock-based unit tests), so
   each such risk needs a *static* countermeasure or it has none at all.
2. **The revision is hand-written and one-way in practice.** A 20-table `upgrade`
   paired with a hand-written `downgrade` is the classic site of asymmetry, and AC-2/AC-3
   — the criteria that would catch it — are exactly the unverifiable ones.
3. **This changeset fixes contracts that three downstream specs must live with.**
   The schema, the `POSTGRES_*` contract, the fixture catalogue and the fixture IDs are
   consumed by SPEC-002/3/4 and by 83 already-written scenarios. Getting them wrong is
   cheap now and expensive after SPEC-002 is built on top.

Severity is `Likelihood × Impact`, rated `Low` / `Medium` / `High`, with `Critical`
reserved for high-likelihood/high-impact risks that would silently invalidate the
enabler for all downstream specs.

## Risks and Countermeasures

### Technical Risks

| ID | Risk | Likelihood | Impact | Severity | Countermeasure |
| --- | --- | --- | --- | --- | --- |
| RISK-001 | **Downgrade is incomplete — residue left after `downgrade base`.** A hand-written `downgrade` for 20 tables, 20 triggers, 1 trigger function, 2 named enum types and the schema itself must drop every object the `upgrade` created. Alembic autogenerate is not in play; nothing checks the two halves against each other. The usual omissions are the native enum types (SQLAlchemy only auto-drops `sa.Enum` types in some code paths), the trigger function, and the schema. Violates REQ-1.3; AC-2/AC-3 cannot catch it. | High | High | Critical | Task 2 must build `downgrade` as the literal mirror of `upgrade` in reverse order, with an explicit `DROP` for each object class: per-table triggers, tables, `base.set_updated_at()`, both enum types (`sa.Enum(..., name=...).drop(bind, checkfirst=False)` or explicit `DROP TYPE base.http_method` / `base.document_type`), then `DROP SCHEMA base`. Both enums must be declared with `create_type=False`/explicit lifecycle so ownership is unambiguous. Phase 1's offline render (`alembic downgrade base --sql`) is the enforcement point: the reviewer diffs the rendered downgrade DDL against the rendered upgrade DDL object-for-object and confirms a matching `DROP` for every `CREATE`. Record the object inventory (20 tables, 20 triggers, 1 function, 2 types, 1 schema) in `docs/db_schema.md` so the count is auditable. |
| RISK-002 | **The revision never executes against PostgreSQL, so any DDL that compiles but does not run ships broken.** Offline `--sql` render proves import and compilation only. Runtime-only failures — FK referencing a table created later in the same revision, an enum used in a column before `CREATE TYPE`, `search_path`/schema-qualification mistakes in raw `DDL()` for the trigger function and `COMMENT ON` statements, a reserved word used unquoted — all pass the static gate. `alembic upgrade head` could fail on first real use, which is SPEC-002's first day. | High | High | Critical | Accept that verification is static and make the static gate as strong as it can be: (a) Task 2 must emit tables in strict FK-dependency order and create both enum types and the trigger function *before* any dependent object; (b) every raw-SQL string (`op.execute`) must be schema-qualified (`base.`) with no reliance on `search_path`; (c) the Phase 1 offline render must be inspected as *SQL*, not merely confirmed to exit 0 — the reviewer reads the emitted statement order and checks that no object is referenced before its `CREATE`; (d) a reviewer-side identifier check for PostgreSQL reserved words and the 63-character identifier limit (trigger names `{table}_set_updated_at` on the longest table names, e.g. `cv_stack_item_experience_link_set_updated_at`, must be verified under 63 chars). The residual unverified risk is surfaced in the final workflow report against AC-1. |
| RISK-003 | **The 20-table contract is under- or mis-delivered relative to spec §6.1.** Twenty tables, each with columns, widths, nullability, defaults, FK actions, unique constraints, `created_at`/`updated_at`, a trigger and `COMMENT ON`, are transcribed by hand from a jsonc spec. A missed table, a missed column, or a wrong FK action is invisible without a database and would only surface as an ORM error in SPEC-002. | Medium | High | High | Task 2 works from the explicit 20-name list in the plan's Reference Contracts as a checklist, and Task 5 (`docs/db_schema.md`) is authored *from the revision*, table by table, making the documentation a second independent transcription pass. Reviewers must cross-check three artifacts pairwise — spec §6.1, the revision, and `docs/db_schema.md` — and treat any disagreement as a defect in the revision, not in the docs. The Phase 2 completion criterion ("every one of the 20 tables appears as a Markdown table matching the migration exactly") is the enforcement point. |
| RISK-004 | **Fixed schema and fixture shape are wrong for the 83 downstream scenarios.** `@spec-002` (42), `@spec-003` (5) and `@spec-004` (36) scenarios in `acceptance/features/` are already written and are user inputs that cannot be edited. If a scenario expects data the §6.1 schema cannot represent (a field, a cardinality, an ordering key), the mismatch is discovered only when SPEC-002 is implemented — after the schema is frozen and the migration is (notionally) applied. | Medium | High | High | Task 6 exists precisely to front-load this: it reads every `@spec-002`/`@spec-003`/`@spec-004` scenario across the six feature files before any fixture or model is authored, and records the derived catalogue in `scripts/seeding/README.md`. Task 6 must be executed as a genuine derivation, not a plausible guess — the catalogue must cite the scenarios that motivate each fixture row. Per the plan's Notes, any expectation the schema cannot represent is **surfaced to the orchestrator as a user-input conflict**; the executor must not bend the schema beyond the recorded F-9 resolutions, and must not edit `acceptance/**`. Reviewers verify `acceptance/**` and `docs/specs/**` are untouched in the changeset. |
| RISK-005 | **Fixture IDs and shapes become a de-facto API for three specs without being marked as such.** Fixtures carry pre-generated UUIDv7 hex IDs and a specific domain-file decomposition. SPEC-002/3/4 tests will pin to those IDs and file names. Any later renumbering or re-decomposition silently breaks downstream work. | Medium | Medium | Medium | Task 6's catalogue in `scripts/seeding/README.md` is the published contract: it must enumerate the domain fixture files, the rows each contains, the shared-lookup ownership rules, and the FK-safe cross-file insert order, and must state explicitly that fixture IDs are stable and downstream-referenced. Task 12 completes the same README with the CLI and environment contract. Reviewers check the README enumerates the actual shipped files with no drift between catalogue and `scripts/seeding/fixtures/`. |
| RISK-006 | **Seeding atomicity is violated without any test noticing.** REQ-2.5/AC-7 require all truncations and inserts in a single transaction with nothing written on failure. Mock-based tests can pass while the real code opens a connection in autocommit, commits per statement, or connects before validation completes. | Medium | High | High | Task 9 must isolate the executor as one function taking an already-open psycopg v3 connection with `autocommit` disabled and `dict_row` row factory, performing every truncate and insert inside one `with conn.transaction()` block with exactly one commit path. Task 10 must order the pipeline load → validate → link → *then* connect. Unit tests must assert on the recorded call sequence of the mock connection/cursor: (a) exactly one commit, (b) no commit on the failure path (a rollback or a propagated exception with no commit), (c) for the invalid-fixture case, that no connection is opened at all — assert the connection factory was never called. Reviewers verify no `autocommit=True` and no stray `conn.commit()` outside the executor. |
| RISK-007 | **Truncate-set and FK-order logic is correct in tests but wrong in ordering against the real schema.** The truncate set (only tables receiving rows) and the FK-safe insert order are hand-derived. A mock records whatever order the code produces, so a test that asserts the code's own ordering is self-fulfilling unless the expected order is derived independently from the schema. | Medium | High | High | The FK-safe order must be written down once, independently, in `scripts/seeding/README.md` (Task 6) derived from the revision's FK graph, and `test_persistence.py` must assert the computed order against that written constant — not against a re-derivation by the same code. Cover explicitly: `document` before `article`; `article` before `topic_article_link` and `article_comment`; `topic` before `topic_article_link`; `api_key` before `admin_audit_log`; `cv_stack_item` and `cv_experience` before `cv_stack_item_experience_link`; `cv_skill_category` before `cv_stack_item_category_link`; `agent_spec` and `document` before `agent_spec_document_link`; `contact` before `message`. Add a negative test that a table receiving zero rows is absent from the truncate set. |
| RISK-008 | **Shared-lookup de-duplication silently loses data.** `base.cv_stack_item` and `base.document` are referenced by two domains each. A naive `dict`-keyed de-duplication is last-write-wins: two rows with the same ID and conflicting payloads collapse without an error, producing a database that differs from the fixtures nobody can inspect. Note F-3's ownership rule is an **orchestrator assumption**, not a user decision. | Medium | High | High | Task 9's de-duplication must compare full payloads on ID collision and raise an explicit error on any conflict — never last-write-wins. Unit tests must cover all three cases: identical duplicate (collapses to one row), conflicting duplicate (raises), and distinct rows (both kept). Ownership per binding item 11 (`cv_stack_item` owned by CV experience; CV skills references by ID only; `document` shared between article and agent-spec domains) must be restated in `scripts/seeding/README.md`, flagged there as an orchestrator assumption open to user override. Cross-file ID references that resolve to no defined row must raise during linking, before any DB interaction. |
| RISK-009 | **Sidecar document content handling is unsafe or produces a wrong derived `size`.** The `content` field holds a path relative to `scripts/seeding/fixtures/`. A path escaping that root (`../`, absolute path, symlink) would read arbitrary files into the database; a text-mode read or an encoding round-trip would break AC-10's byte-identity; a fixture-supplied `size` must be rejected rather than trusted. | Medium | Medium | Medium | Task 7's document model must: resolve the path against the fixtures root and reject any resolved path outside it (compare resolved absolute paths, covering `..` and symlinks) and reject absolute paths outright; read the file in **binary mode** (`Path.read_bytes()`) with no decode; derive `size` as `len(content_bytes)`; and reject a fixture that supplies `size` explicitly (pydantic v2 `model_config = ConfigDict(extra="forbid")` plus an explicit check). Missing file and empty file are validation errors. Unit tests cover traversal rejection, absolute-path rejection, missing file, empty file, explicit-`size` rejection, and correct derived size for a known byte string. |
| RISK-010 | **Untested code ships in the alembic component, the wrapper and both Dockerfiles.** By binding decision the alembic component has no unit tests; `alembic/src/main.py`, `alembic/src/config.py`, `env.py` and both Dockerfiles have zero automated coverage. The AC-4 fail-fast behaviour, in particular, is asserted by no test and executed by no CI job. | High | Medium | High | Make the substitute checks explicit and mandatory rather than implicit: (a) the wrapper's missing-variable behaviour is verified manually in Phase 1 by running `alembic/src/main.py` with `ALEMBIC_REVISION` and then `ALEMBIC_COMMAND` unset and confirming a non-zero exit whose message names the missing variable — this is a stated Phase 1 completion criterion and its result must be reported; (b) `ALEMBIC_COMMAND` must be constrained to `{upgrade, downgrade}` by the `pydantic_settings` model (a `Literal`), so the invalid-value case is enforced by type rather than by a hand-written branch; (c) both images must actually be built in Phase 1/Phase 3 with `--platform linux/amd64 --provenance=false`, not merely declared buildable; (d) code review of `alembic/` is the primary quality gate and reviewers should be told so. `quality-controller` must not flag `[PY-025]`–`[PY-028]` against `alembic/` (user-approved deviation). |
| RISK-011 | **Python 3.14 pin or `uuid.uuid7` usage regresses to something that does not exist.** The spec's `uuid.uuidv7` is a typo. Any image below 3.14 lacks stdlib `uuid.uuid7`, and dependency wheels (psycopg v3, pydantic v2, alembic, structlog, pytest-postgresql) may not all be available for 3.14 on the slim base, tempting a silent downgrade of the base image. | Medium | High | High | Both Dockerfiles pin a Python 3.14 slim tag explicitly; reviewers verify the tag in both files and reject any lower version. The string `uuid.uuidv7` must not appear anywhere in the changeset — a grep-level review check. If a dependency has no 3.14 wheel, the resolution is to surface the conflict to the orchestrator (pin a compatible version, or request a user decision on a UUIDv7 backport), **not** to lower the base image. Fixture IDs are pre-generated and stored literally, so fixture authoring must not depend on runtime `uuid7()` availability. |
| RISK-012 | **A test in the seeding suite requires a PostgreSQL binary.** `pytest-postgresql` is pinned by binding decision but its process/client fixtures need a `postgres` executable that is not present. Importing or requesting such a fixture makes the suite fail inside the Dockerfile tests stage — or, worse, someone "fixes" it by installing PostgreSQL into the image. | Medium | Medium | Medium | No test may request a `pytest-postgresql` fixture that spawns or connects to a server; tests drive the persistence layer's pure functions directly and the executor through mock connection/cursor objects. The Dockerfile tests stage is the enforcement mechanism and must run in an image with **no** PostgreSQL binary — the seeding runtime/test images must not install a `postgres` server package. Reviewers check `conftest.py` and every test module for server-spawning fixtures, and check the Dockerfile for any postgres server install. |
| RISK-013 | **A secondary index is created.** Spec §6.1 bans indexes other than those implicitly backing PK/unique constraints, but `index=True` on a SQLAlchemy `Column` is a reflex, and the F-9b/c/d unique constraints are easy to render as `op.create_index` instead. | Medium | Medium | Medium | Task 2 must express uniqueness only via `UniqueConstraint` / `sa.UniqueConstraint` and never `op.create_index` or `index=True`. The Phase 1 offline SQL render is grepped for `CREATE INDEX` — any occurrence that is not the implicit index emitted by a PK/unique constraint is a defect. Reviewers apply the same grep to the revision source. |
| RISK-014 | **`docs/db_schema.md` drifts from the revision, defeating the only closable acceptance criterion.** AC-11 is the single criterion this changeset can close, and it is closed by documentation review. If the document is generated from the spec rather than from the delivered revision, or if the F-9 resolutions and both waivers are omitted, the one verifiable deliverable is also wrong — and downstream specs read this document as the schema's source of truth. | Medium | High | High | Task 5 is sequenced after Task 2 and must be authored from the revision file. It must contain: one Markdown table per physical table with column names, types/widths, nullability, defaults and constraints; at least one Mermaid diagram covering all 20 entities and their relationship cardinalities; the `[PG-005]` waiver note for `base.article.document_id` (nullable FK, `ON DELETE CASCADE` retained); the `[PG-014]` waiver covering `base.subagent.inputs/outputs` **and** `base.admin_audit_log.payload/response`; and an explicit record of every F-9a–f resolution including the final chosen widths. If the executor refines any width or constraint in Task 2, `docs/db_schema.md` must be updated in the same changeset. Reviewers diff the document against the revision table by table. |
| RISK-015 | **The `POSTGRES_*` / `ALEMBIC_*` contract diverges between the two components.** Two independently written `src/config.py` files implement the same contract. Divergent variable names, differing defaults for `POSTGRES_PORT`, or a password field that is not a `SecretStr` in one component produce a contract that SPEC-002 and the future Kubernetes jobs cannot rely on — and risk leaking a password into structured logs. | Medium | Medium | Medium | Both components implement the contract table in the work plan's Reference Contracts verbatim: `POSTGRES_HOST`/`USER`/`PASSWORD`/`DB` required with no defaults, `POSTGRES_PORT` defaulting to `5432`, `POSTGRES_PASSWORD` typed as `SecretStr` in **both** components. Missing required variables fail at config validation, before any work. Both component READMEs document the identical table with required/optional status and defaults; reviewers diff the two READMEs' tables against each other and against the plan. No config object, connection string, or exception message may be logged in a way that renders the password — structlog calls must not pass the whole settings object. |
| RISK-016 | **`ON DELETE CASCADE` on the nullable `base.article.document_id` deletes article rows.** The user declined the `SET NULL` alternative (F-4b) and retained cascade, so deleting a document deletes the article metadata row. This is now intended behaviour, but it is surprising and downstream specs will build deletion flows on top of it. | Low | High | Medium | Implement exactly as decided (nullable FK, `ON DELETE CASCADE`) — do not silently "improve" it to `SET NULL`. Record the behaviour and its consequence explicitly in `docs/db_schema.md` alongside the `[PG-005]` waiver note, so SPEC-002/4 authors writing document-deletion endpoints see it. Reviewers treat any deviation from cascade as a defect against a binding decision. |
| RISK-017 | **Timestamp and trigger conventions are applied inconsistently across 20 tables.** `created_at`/`updated_at` with `server_default=sa.func.now()` on `TIMESTAMP WITH TIME ZONE`, plus a `{table}_set_updated_at` trigger per table, is 40 columns and 20 triggers of repetition. Omitting the trigger on a few tables, or slipping in `DEFAULT (now() AT TIME ZONE 'utc')`, is invisible without a database. | Medium | Medium | Medium | Task 2 generates the timestamp columns and the trigger DDL from a single shared helper/loop over the table list rather than by copy-paste, so the convention cannot vary per table. The forbidden `now() AT TIME ZONE 'utc'` form must not appear anywhere — a grep-level review check. The Phase 1 offline render must show exactly 20 `CREATE TRIGGER` statements and a `COMMENT ON` for the schema, each table, the trigger function and each trigger; the reviewer counts them against the 20-table list. |
| RISK-018 | **Scope leakage into user inputs or out-of-scope infrastructure.** Task 6 reads `acceptance/**`; a plausible-looking "small fix" to a feature file, the spec, `.pre-commit-config.yaml`, `.flake8`, or the existing root `Makefile` targets would corrupt user inputs. Equally, an executor may be tempted to add a docker-compose file or a CI workflow to make AC-1 … AC-10 verifiable — all explicitly waived and out of scope. | Medium | Medium | Medium | Enforce the plan's Review Scope as a hard boundary: `docs/specs/**` and `acceptance/**` are read-only; `.pre-commit-config.yaml` and `.flake8` are untouched; the root `Makefile`'s existing `scan-secrets`/`claude` targets are preserved and only thin `run-migrations`/`seed` delegation targets may be added. No `docker-compose.yml`, no `.github/workflows/**`, no PostgreSQL provisioning is added — the verification gap is *reported*, not closed. Reviewers check the changeset file list against this boundary and flag any file outside it. |
