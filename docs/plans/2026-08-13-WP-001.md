# Work Plan: SPEC-001 Database and Schema Implementation

Work Plan ID: WP-001
Created Date: 2026-08-13
Type: feature
Spec: docs/specs/SPEC-001.md
Scale: Large
Description: Deliver the SPEC-001 database enabler — a single alembic revision creating/dropping the PostgreSQL `base` schema (20 tables), containerised migration and seeding runners with component Makefiles, pydantic-validated JSON domain fixtures with sidecar document content, and Markdown schema documentation.
Estimated Impact: ~46 files (all new except README.md and the root Makefile)

## Objective

Provide the persistence foundation for the personal-website rebuild: every entity in
SPEC-001 §6.1 modelled in PostgreSQL under the `base` schema, managed by a single
alembic revision; a container that runs migrations from environment configuration; a
container that seeds a migrated database from validated JSON domain fixtures; and
`docs/db_schema.md` documenting the schema. Nothing in this changeset is user- or
API-facing; SPEC-002/3/4 build on it.

## Background

The repository is greenfield on branch `feature/v2`: only `docs/`, `acceptance/`,
`README.md`, the root `Makefile`, `.flake8`, and `.pre-commit-config.yaml` exist. Every
source path in this plan is a new file. The spec was reviewed at the Step 0 gate and a
set of **binding user decisions** was recorded in `docs/specs/SPEC-001-REVIEW.md`
sections 6a and 6b. Those decisions override the spec where they conflict and are
restated where load-bearing in this plan; downstream agents must read them in full.

Key binding decisions (see SPEC-001-REVIEW.md §6a/§6b for the authoritative text):

1. Directories per spec §6.2 stand: root-level `alembic/` and `scripts/seeding/`.
   `README.md` is amended in this changeset (tree, TOC, and component prose).
2. Document fixture content is a **sidecar file reference**: the fixture `content`
   field holds a path relative to `scripts/seeding/fixtures/`; the seeder reads that
   file as bytes; `size` is **derived** by the pydantic document model from the file's
   byte length (never fixture-supplied).
3. Migration CI job, docker-compose, and any provisioned PostgreSQL instance are
   **out of scope**. AC-1 … AC-10 are therefore not verifiable in this changeset (see
   traceability table below) — this must be surfaced at the end of the workflow.
4. `[PG-005]` is waived for `base.article.document_id` (direct nullable FK,
   `ON DELETE CASCADE`). The `[PG-014]` waiver covers `base.subagent.inputs/outputs`
   AND `base.admin_audit_log.payload/response`. Both waivers are recorded in
   `docs/db_schema.md`.
5. Unit tests are for the **seeding script only**; the alembic component has none.
   Tests mock the database — no real PostgreSQL server is started (see Verification
   Strategy for the pytest-postgresql resolution).
6. Both container images pin a **Python 3.14 slim** base and use stdlib
   `uuid.uuid7()` (the spec's `uuid.uuidv7` is a typo — never use that name).
7. Fixtures must satisfy the data expectations of the existing `@spec-002`,
   `@spec-003`, and `@spec-004` scenarios in `acceptance/features/` — a dedicated task
   derives those expectations before fixtures are authored.
8. Unresolved schema details (review F-9a–f) are resolved by the implementer using
   the conventions visible in §6.1; **every such decision is recorded in
   `docs/db_schema.md`** (see Reference Contracts for the plan-level resolutions).
9. `argparse` defaults are sourced from a `pydantic_settings` config in
   `src/config.py` — no entrypoint shell wrapper.
10. The full `POSTGRES_*` contract is fixed in this changeset and documented in both
    component READMEs (see Reference Contracts).
11. Shared lookup ownership: `base.cv_stack_item` is owned by the CV experience
    domain fixture (CV skills references by ID only); `base.document` is shared
    between the article and agent-spec domains; the seeder de-duplicates shared rows
    so each is inserted exactly once.
12. Makefiles are component-level (`alembic/Makefile` → `run-migrations`,
    `scripts/seeding/Makefile` → `seed`). `.pre-commit-config.yaml` is untouched.

The spec and the acceptance suite are user inputs: no task creates, modifies, or
removes specs, feature files, or scenarios.

## Verification Strategy

No live PostgreSQL instance exists in this changeset (binding decision 3), so
verification is static and mock-based:

- **Phase 1 early verification point**: render the revision's SQL offline
  (`alembic upgrade head --sql` and `alembic downgrade base --sql` with a dummy
  connection URL in offline mode). This proves the revision imports, compiles, and
  emits DDL for the schema, both enums, the trigger function, all 20 tables,
  triggers, and comments — without a server. Inspect the rendered downgrade for
  complete residue removal (AC-2's static proxy).
- **Unit tests (seeding only)**: `pytest` under `scripts/seeding/tests/`, run
  locally and in the Dockerfile tests stage. **pytest-postgresql resolution**: the
  binding decision names `pytest` + `pytest-postgresql` with the database mocked and
  no real server started. pytest-postgresql's process fixtures require a `postgres`
  executable, which is not available; therefore no test may use a fixture that
  spawns or connects to a server. `pytest-postgresql` is pinned in the test
  requirements to honour the decision, but tests exercise the persistence layer's
  pure functions (SQL construction, truncate-set computation, FK ordering,
  de-duplication) directly and drive the executor through mock
  connection/cursor objects (`unittest.mock` or hand-rolled fakes recording executed
  statements). The Dockerfile tests stage must pass in an image with no PostgreSQL
  binary — this is the enforcement mechanism.
- **Fixture verification**: the unit suite loads the real shipped fixtures through
  the real models (Task 11), proving validation, ID cross-references, and non-empty
  sidecar content without a database.
- **Container verification**: both images build with
  `--platform linux/amd64 --provenance=false`; the seeding image's tests stage runs
  the unit suite during build.
- **Lint/format**: `flake8` (repo `.flake8`, max-line-length 88, black-compatible)
  and `black` over all new Python.
- **AC-11**: documentation review of `docs/db_schema.md` against the Task 2 revision.

Whole-changeset validation runs in the pipeline review stage.

## Failure Modes

- [ ] `ALEMBIC_REVISION` or `ALEMBIC_COMMAND` unset → wrapper raises an explicit
      error naming the missing variable; container exits non-zero (AC-4 behaviour)
- [ ] `ALEMBIC_COMMAND` not in `{upgrade, downgrade}` → explicit error, non-zero exit
- [ ] Required `POSTGRES_*` variable unset → config validation fails at startup
      (both components), before any work is attempted
- [ ] Unreachable database → non-zero exit, no partial state, clear structlog error
- [ ] Fixture violating its pydantic model → `ValidationError`, non-zero exit,
      raised before any database connection is opened (AC-7 behaviour)
- [ ] Fixture `content` sidecar path missing, escaping `scripts/seeding/fixtures/`,
      or empty → validation error before any database interaction
- [ ] Fixture supplying an explicit document `size` → rejected; `size` is derived
      only
- [ ] Cross-file FK reference to an ID absent from every fixture (e.g. CV skills
      referencing an unknown stack-item ID) → linking error before any DB writes
- [ ] Shared lookup row (`base.document`, `base.cv_stack_item`) appearing in two
      domain files with the same ID but conflicting payloads → error, never silent
      last-write-wins de-duplication
- [ ] Truncation of a table that receives no fixture rows → forbidden; only tables
      receiving at least one row are truncated (cascade side-effects are permitted
      per REQ-2.5)
- [ ] Any insert executed outside the single seeding transaction, or a commit before
      all inserts succeed → violates REQ-2.5 atomicity
- [ ] Downgrade leaving residue (either enum type, the trigger function, any
      trigger, the schema, or the alembic version table state) → violates REQ-1.3
- [ ] A secondary index created anywhere → violates spec §6.1; only implicit
      PK/unique-backing indexes are allowed
- [ ] Use of `uuid.uuidv7` (nonexistent) instead of `uuid.uuid7()`, or a base image
      below Python 3.14 (which lacks `uuid.uuid7`)

## Reference Contracts

**The 20 physical tables** (spec §6.1; the single revision must create all of them):
`base.contact`, `base.message`, `base.topic`, `base.article`,
`base.topic_article_link`, `base.article_comment`, `base.document`, `base.subagent`,
`base.cv_stack_item`, `base.cv_experience`, `base.cv_experience_responsibility`,
`base.cv_stack_item_experience_link`, `base.cv_education`, `base.api_key`,
`base.admin_audit_log`, `base.agent_spec`, `base.agent_spec_document_link`,
`base.cv_skill_category`, `base.cv_stack_item_category_link`, `base.project`.

**Primary keys**: `VARCHAR(32)`, UUIDv7 with hyphens stripped, generated with stdlib
`uuid.uuid7().hex` (Python 3.14). Fixture files carry pre-generated IDs.

**Timestamps**: `TIMESTAMP WITH TIME ZONE`; `created_at`/`updated_at` on every table
with `server_default=sa.func.now()`; never `DEFAULT (now() AT TIME ZONE 'utc')`.

**Trigger function**: `base.set_updated_at()` (one per schema), per-table triggers
named `{table}_set_updated_at`, with `COMMENT ON` for the function and each trigger.
Downgrade drops all triggers and the function.

**Native enum types** (named so downgrade can drop them and docs can cite them —
F-9e resolution):

- `base.http_method` — values `get`, `post`, `put`, `patch`, `delete`
  (`base.admin_audit_log.method`)
- `base.document_type` — values `spec`, `acceptance`, `other`
  (`base.agent_spec_document_link.document_type`)

**F-9 resolutions fixed by this plan** (Task 2 implements; Task 5 records in
`docs/db_schema.md`; the executor may refine widths but every final value must be
recorded):

- F-9a: non-PK string columns get explicit widths — bounded `VARCHAR(n)` for names,
  emails, titles, filenames and similar short fields; `TEXT` for free-form prose
  (message/comment/description bodies). FK columns are `VARCHAR(32)` to match PKs.
- F-9b: unique constraint on `base.api_key.api_key`.
- F-9c: unique constraint on `base.cv_skill_category.category`.
- F-9d: unique constraint on `base.agent_spec_document_link (spec_id, document_id)`;
  every link table has a unique constraint over its link tuple.
- F-9f: `base.admin_audit_log.api_key_id` FK is `ON DELETE RESTRICT`.
- Lookup-table names (`base.topic.name`, `base.cv_stack_item.name`) unique per spec.

**Waivers** (recorded in `docs/db_schema.md`): `[PG-005]` waived for
`base.article.document_id` (direct nullable FK, `ON DELETE CASCADE` retained);
`[PG-014]` waived for `base.subagent.inputs/outputs` and
`base.admin_audit_log.payload/response` (JSONB per spec).

**Environment variable contract** (fixed here; documented in both component READMEs
— this is what the future Kubernetes jobs and SPEC-002's API consume):

| Variable | Required | Default | Consumers |
| --- | --- | --- | --- |
| `POSTGRES_HOST` | yes | — | both containers |
| `POSTGRES_PORT` | no | `5432` | both containers |
| `POSTGRES_USER` | yes | — | both containers |
| `POSTGRES_PASSWORD` | yes | — (SecretStr) | both containers |
| `POSTGRES_DB` | yes | — | both containers |
| `ALEMBIC_REVISION` | yes (no default; raise if unset) | — | migrations container |
| `ALEMBIC_COMMAND` | yes (`upgrade`\|`downgrade` only; raise if unset) | — | migrations container |

**Seeder CLI contract** (REQ-2.2 + binding decision 9): `argparse` arguments for
host/port/user/password/dbname whose defaults come from the `pydantic_settings`
config, so `docker run -e POSTGRES_...` works with no shell wrapper and explicit CLI
arguments still override.

**Domain fixture decomposition** (proposal — Task 6 confirms and records the final
catalogue and insert order in `scripts/seeding/README.md`): one JSON file per domain
aggregate — contacts (contact + messages), blog (topics + articles + comments +
embedded owned documents), agent specs (spec + document links + embedded documents),
CV experience (experiences + responsibilities + owned stack items + links), CV skills
(categories + stack-item ID references), CV education, subagents, projects, API keys,
admin audit log (API-key ID references). FK-safe insert order runs parents before
children (e.g. document → article → topic links → comments; api_key →
admin_audit_log; cv_stack_item → experience links/category links).

**Docker/build contract**: multi-stage Dockerfiles; Python 3.14 slim (Debian-based)
runtime; seeding image has a tests stage running pytest; builds use
`--platform linux/amd64 --provenance=false` in the make targets.

**Coding standards to load** (via the `coding-standards` skill at
`/etc/coding-standards/`): `GENERAL.md`, `databases/POSTGRES.md` (+
`examples/POSTGRES/timestamp-columns.md`, `examples/POSTGRES/link-tables.md`),
`python/GENERAL.md` (+ examples for data-models, config, logging,
persistence-postgres), `general/DOCKER.md`, `python/DOCKER.md` (+
`examples/DOCKER/two-stage-build.md`), `general/MAKEFILES.md`, `general/LOGGING.md`.
