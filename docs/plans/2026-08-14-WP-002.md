# Work Plan: SPEC-002 Public REST API Implementation

Work Plan ID: WP-002
Created Date: 2026-08-14
Type: feature
Spec: docs/specs/SPEC-002.md
Scale: Large
Description: Build the Golang/gin public REST API (12 endpoints across six routers), a pgx-based persistence layer over the read-only `base` PostgreSQL schema, and the OpenAPI/Postman documentation artifacts.
Estimated Impact: ~35 files (new `api/` component, `docs/openapi.yaml`, `docs/postman/collection.json`, `.pre-commit-config.yaml`, root `README.md`)

## Objective

Deliver the public REST API defined by SPEC-002 so the SPEC-003 frontend has a data source: health/version, CV, agents/specs, articles/comments, messages, and projects endpoints, backed by the existing `base` PostgreSQL schema, with API documentation artifacts at `docs/openapi.yaml` and `docs/postman/collection.json`.

## Background

The repository currently contains the database schema and seeding (SPEC-001) but no `api/` component. The root `README.md` documents `api` as "Golang source code for the REST API" — the component location is fixed by monorepo convention: each component owns its own Makefile and README, and `.pre-commit-config.yaml` drives lint via `make -C <component> lint`.

The database is **read-only for this work**: `docs/db_schema.md` is the source of truth and `alembic/migrations/versions/0001_initial_base_schema.py` must not change. IDs are VARCHAR(32) hex UUIDv7 (no hyphens) generated by the application, matching the rendering used by `scripts/` seeding.

A spec review exists at `docs/specs/SPEC-002-REVIEW.md`. The user has made **binding decisions** that override spec text where they conflict; they are restated in full in the Notes section and are mandatory inputs to every task.

Applicable coding standards (collected via the standards tree; all tasks must load them):

- `GENERAL.md` (GEN-001..006), `general/API.md` (API-001..012), `general/LOGGING.md`, `general/MAKEFILES.md`
- `golang/GENERAL.md` (GO-001..045) and `golang/API.md` (GO-API-001..005), with examples: `config.md`, `unittests.md`, `logging.md`, `persistence-interface.md`, `persistence-anti-pattern.md`, `persistence-postgres.md`, `controller-api.md`, `api-anti-pattern.md`

Key structural mandates: flat directory layout with snake_case filenames ([GO-008]/[GO-006], no cmd/internal nesting), Go >= 1.25 ([GO-001]; sandbox toolchain is go1.24.4 but `GOTOOLCHAIN=auto` fetches go1.25.0 on demand), gin + gin-contrib/cors + pgx/v5 + pgxpool + viper + validator/v10 + logrus JSON + testify ([GO-API-001], [GO-API-005], [GO-044]/[GO-045], [GO-018]/[GO-023], [GO-012], [GO-033], [GO-032]), persistence behind an interface with a `New` constructor holding the pool singleton ([GO-034]/[GO-035]/[GO-039]), IDs/timestamps generated inside the persistence layer ([GO-041]), handler signature `EndpointNameHandler(c *gin.Context) JSONResponse` ([GO-API-004]).

## Failure Modes

- [ ] Toolchain mismatch: sandbox go1.24.4 vs required Go >= 1.25 — all build/test commands must run with `GOTOOLCHAIN=auto` (verified to fetch go1.25.0)
- [ ] Duplicate contact created when message insert fails or when email differs only by case/whitespace (REQ-5.2/5.3/5.4)
- [ ] Orphaned contact left behind if the message insert fails outside a transaction (REQ-5.4)
- [ ] Client-supplied `read`/`submitted_at` leaking into persistence (must be silently dropped by tolerant binding, REQ-5.5/AC-38)
- [ ] Whitespace-only name/message/comment passing validation — emptiness must be evaluated after trimming (binding decisions 11)
- [ ] Values exceeding writable column widths reaching the DB — enforce as 400: `contact.name`/`organization` VARCHAR(255), `contact.email` VARCHAR(320), `article_comment.author` VARCHAR(255) (`message.content`/`article_comment.comment` are TEXT)
- [ ] Existence disclosure: hidden (`display=false`), doc-less, or restricted-document articles must return the identical 404 envelope on every article endpoint, including POST comment
- [ ] Restricted spec/supporting documents leaking through the spec listing or content endpoint (REQ-4.5/4.6/4.10)
- [ ] Spec violating the at-most-one-primary-document invariant crashing the listing — must be omitted with a warning log (binding decision 10)
- [ ] Non-deterministic list ordering across identical requests — every list query needs an explicit deterministic ORDER BY (binding decision 4)
- [ ] `/v1/cv` or `/v1/messages` triggering a 301/307 trailing-slash redirect — register both `""` and `"/"` (binding decision 9)
- [ ] CORS preflight responding with wrong status or method/header list — must be 204 with the exact §6.2 sets; disallowed origin → 204 with no `Access-Control-Allow-Origin` header
- [ ] Error `details` leaking SQL, schema, or internal structure (§6.1.0) — generic message on 500s
- [ ] Health endpoint returning 200 while the pool is unreachable (REQ-1.5)
- [ ] Any authentication/API-key/admin logic creeping in — explicitly forbidden here (binding decision 1, belongs to SPEC-004)
- [ ] Accidental writes to the DB schema, alembic migrations, or `acceptance/features/` — all read-only user inputs
- [ ] Tech-stack items without a category appearing in the CV skills map (REQ-2.6)
- [ ] Agents with no declared schemas omitting `inputs`/`outputs` instead of returning `{}` (REQ-4.2)

## Reference Contracts

- **Endpoints (12)**: as tabled in SPEC-002 §2; routers Base `/v1`, CV `/v1/cv`, Articles `/v1/articles`, Agents `/v1/agents`, Messages `/v1/messages`, Projects `/v1/projects`, all groups created from the `/v1` base group.
- **Success/error shapes**: JSON, 200 default; error envelope `{"error": string, "details": string}` (§6.1.0); 4xx validation errors name the failing field and reason; 500 body `{"error": "Internal Server Error", "details": "Something went wrong."}`.
- **Creation responses**: `POST /v1/messages` → 201 `{"message_id": string}`; `POST /v1/articles/:article_id/comment` → 201 `{"comment_id": string}` (asserted verbatim by acceptance features).
- **Content endpoints**: `GET /v1/agents/specs/:id/:document_id` and `GET /v1/articles/:article_id/content` return raw bytes with content type exactly `binary/octet-stream` (blog.feature:29).
- **CORS (§6.2)**: origins `http://localhost:9000`, `https://psauerborn.dev`, `https://dev.psauerborn.dev`; headers `Content-Type, Accept, Accept-Language, Content-Language`; methods `GET, POST, PATCH, PUT, DELETE, OPTIONS`; preflight 204 (api.feature:35-37); disallowed origin → 204 without `Access-Control-Allow-Origin`.
- **Response schemas**: §6.1.1–§6.1.12 verbatim; the article listing's JSON field is named `created_at`, exactly as §6.1.8 specifies, but its **value** is read from the `base.article.authored_at` column (the authoring timestamp), not `base.article.created_at` (an audit column defaulting to `now()`) — binding decision 4; version value sourced from viper-loaded config (binding decision 8).
- **IDs**: VARCHAR(32) hex UUIDv7 without hyphens, generated in the persistence layer.
- **DB**: `docs/db_schema.md` is the source of truth; schema `base`; read-only except INSERTs into `base.contact`, `base.message`, `base.article_comment`.
- **Handler pattern**: `EndpointNameHandler(c *gin.Context) JSONResponse` on a controller struct holding the persistence singleton; `NewRouter` registers everything ([GO-API-002..004]).

## Notes

**Binding user decisions** (from the review of `docs/specs/SPEC-002-REVIEW.md`; they override spec text where they conflict and bind every downstream task):

1. REQ-4.7: specs with `display=false` are excluded unconditionally. Implement NO authentication, API key, or admin role anywhere — that is SPEC-004.
2. POST request bodies use tolerant JSON binding (gin `ShouldBindJSON`, NOT `DisallowUnknownFields`): unknown fields are ignored, so client-supplied `read`/`submitted_at` are silently dropped per REQ-5.5/AC-38.
