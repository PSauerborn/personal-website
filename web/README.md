# web

The frontend application: a Next.js App Router project written in TypeScript and
styled with Tailwind CSS, with shadcn/ui primitives under `components/ui`. It is
a sibling of `api/` in this monorepo and is always invoked from the repository
root via `make -C web <target>`.

## Requirements

- Node 22 or higher (`[JS-001]`)
- Docker and the Compose plugin, for the container workflow below

### Versions

The majors below are the ones this application is written against, and they are
pinned as caret ranges in `package.json`. They are recorded here because the
combinations are not interchangeable: Tailwind 4 uses the CSS-first `@theme`
syntax rather than a `tailwind.config.js`, the shadcn/ui primitives under
`components/ui` were generated by the CLI for that major, and React 19 changes
the ref and `use()` APIs the components rely on. Reading a version here tells
you which documentation applies.

| Package      | Major | Notes                                                     |
| ------------ | ----- | --------------------------------------------------------- |
| Node         | 22    | `engines.node` is `>=22`; the Dockerfile pins a 22 digest |
| Next.js      | 16    | App Router, `output: 'standalone'`                        |
| React        | 19    | with `react-dom` 19                                       |
| Tailwind CSS | 4     | CSS-first `@theme`, via `@tailwindcss/postcss` 4          |
| TypeScript   | 5     | `strict` mode                                             |
| Vitest       | 4     | with jsdom 27 and React Testing Library 16                |
| ESLint       | 9     | flat config, with `eslint-config-next` 16                 |
| Prettier     | 3     | invoked by `make -C web format`                           |

These are majors only. The **exact** resolved versions of every direct and
transitive dependency live in `web/package-lock.json`, which is committed and is
the authority: install with `npm ci` so the lockfile is honoured rather than
re-resolved.

## Running locally

```bash
cd web
npm ci                # install from the committed lockfile
cp .env.example .env  # then edit the values
npm run dev           # http://localhost:9000
```

### Why port 9000

The development server and the container both bind **port 9000**, not Next's
default 3000. This is not a preference: the API pins its CORS allowlist to the
single origin `http://localhost:9000` (`api/router.go`), and REQ-1.7 requires
the browser to call the API directly, with no route handler proxying on this
side. Serving the frontend on any other port therefore breaks every client-side
API call, and nothing in this component's test suite would catch it. The port is
fixed in three places that must agree: `next dev -p 9000` in `package.json`,
`ENV PORT=9000` in `Dockerfile`, and the unparameterised `9000:9000` mapping of
the `web` service in the repository's `docker-compose.yaml`.

Pages are server-rendered from data fetched from the API, so a run without a
reachable API answers `500` rather than an empty page. Point `API_BASE_URL` at a
running API — `docker compose up -d --build postgres api` from the repository
root (with `POSTGRES_PASSWORD` exported) is the quickest way to get one.

## Running the production build

`next.config.ts` sets `output: 'standalone'`, so `npm run build` emits a
self-contained server bundle under `.next/standalone`. That bundle carries the
server and its traced dependencies only — the static assets are **not** copied
into it, so they have to be placed alongside the server before it is started
(the `Dockerfile` does exactly this). `npm start` is deliberately not used and
Next warns against it under `output: 'standalone'`:

```bash
npm run build
cp -r .next/static .next/standalone/.next/static
HOSTNAME=0.0.0.0 PORT=9000 node .next/standalone/server.js  # http://localhost:9000
```

`HOSTNAME=0.0.0.0` matters: the standalone server otherwise binds the machine's
hostname, and a published container port then reaches nothing.

## Running under docker compose

The repository's `docker-compose.yaml` builds this component as the `web`
service (build context `./web`), publishes it on `9000:9000`, joins it to the
`personal-website` network and starts it only once the `api` service is
healthy. From the repository root:

```bash
export POSTGRES_PASSWORD=<password>   # no default; the stack will not start without it
docker compose up -d --build          # postgres :5432, api :8080, web :9000
docker compose logs -f web
docker compose down
```

`--build` is required on the first run and after any change under `web/`,
because the image is built from source rather than pulled. It is also required
after any change to `NEXT_PUBLIC_API_BASE_URL` — see below.

## Make targets

| Target               | Action                                 |
| -------------------- | -------------------------------------- |
| `make -C web lint`   | run eslint over the application        |
| `make -C web format` | format every source file with prettier |
| `make -C web build`  | produce a production build             |
| `make -C web test`   | run the vitest suite                   |
| `make -C web audit`  | report advisories against the tree     |

`make -C web audit` runs `npm audit --audit-level=high`, failing when a package
in `package-lock.json` carries a high or critical advisory. It is **not** a
pre-commit hook: it needs the registry, and wiring it into the hooks would break
every offline commit. Run it in CI and by hand before bumping a dependency.

The WP-003 risk plan names this countermeasure as `npm audit --omit=dev` "or
equivalent"; `--audit-level=high` is the equivalent that was chosen, and the two
flags are not alternatives to each other. `--omit=dev` narrows _which packages_
are audited, and narrowing them is wrong here: almost the whole toolchain —
Next, TypeScript, ESLint, Vitest, jsdom — is a devDependency that executes on
developer and CI machines against this repository's source, so excluding it
would hide the advisories most likely to matter. `--audit-level=high` instead
audits the entire tree and narrows _what fails the command_ to high and
critical, which keeps the target usable as a gate rather than a wall of
low-severity transitive noise. Reviewers reconciling the two documents should read
the risk plan's wording as the intent (audit the dependency tree from a Make
target) and this flag as the implementation of it.

## Environment variables

| Variable                   | Read at        | Description                                                                                                                                                                                                                                                                                              |
| -------------------------- | -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `API_BASE_URL`             | **runtime**    | Base URL of the API used by Server Components and route handlers. Read from the process environment on every request, so changing it on a running container takes effect without a rebuild.                                                                                                              |
| `NEXT_PUBLIC_API_BASE_URL` | **build time** | Base URL of the API used by browser requests from client components. `NEXT_PUBLIC_*` values are **inlined into the client bundle by `next build`**; setting one in the runtime environment of an already-built image has **no effect**. It must be supplied as a build argument when the image is built. |
| `LOG_LEVEL`                | **runtime**    | Verbosity of the server-side log, one of `debug`, `info`, `warn`, `error`. Defaults to `info`; an unrecognised value falls back to the default rather than failing the process. Read per record, so turning a running container up or down needs a restart at most, never a rebuild.                     |

`web/.env.example` carries the same note and is the reference for a local
`.env`.

### Build time vs runtime, concretely

Confusing the two is the failure mode this component is most exposed to
(RISK-001), and it fails **silently**: nothing errors, no test goes red, the
browser simply issues its requests against whatever origin the image happened to
be built with.

- `API_BASE_URL` is read from the process environment on every request by
  Server Components. It is an ordinary runtime variable: set it under
  `environment:` in compose (`http://api:8080`, the API's service name and
  container-internal port, because Server Components run inside the compose
  network), with `-e` on `docker run`, or in `.env` locally. Changing it takes
  effect on restart, with no rebuild.
- `NEXT_PUBLIC_API_BASE_URL` is consumed by `next build`, which substitutes the
  literal string into the client bundle. It is declared as an `ARG` in the
  builder stage of `Dockerfile` and promoted to an `ENV` immediately before the
  build, with no default — an unset value yields a bundle whose requests go
  nowhere, which is easier to notice than a wrong-but-plausible origin. In
  compose it is supplied as a `build.args` entry, and its value is the origin
  the **browser** reaches the API on (the host-side half of the API's port
  mapping, `http://localhost:8080` by default), not the compose service name.
  Changing it requires `docker compose up -d --build`; putting it under
  `environment:` does nothing at all.

  Leaving it unset is quieter than the note above suggests, so it is worth
  naming the symptom: the browser-side surfaces — the blog comments thread and
  the contact form — make **no request at all**, rather than a failing one. Two
  things go wrong together. The client has no base URL to build a request from,
  and `next.config.ts` derives the CSP `connect-src` directive from this same
  variable, so the policy does not name the API origin and would refuse the
  request even if one were made. Nothing appears in the network log to explain
  it. `next build` and `next dev` now print a warning when the variable is
  missing; locally, `cp .env.example .env` is the fix, and both `next dev` and
  `next build` read that file automatically.

## Logging

`lib/logger.ts` writes one JSON object per line to stdout — `message`,
`timestamp` (Unix epoch seconds) and `level`, with event context in dedicated
sibling fields rather than interpolated into the message. There is no logging
package behind it, by decision: the application needs one levelled line on
stdout, and Next.js already forwards server output there, where the container
log driver collects it (`docker compose logs -f web`).

The module is **server-only**. Everything a client component imports is bundled
and shipped to the browser, so importing it from a file carrying `'use client'`
would put the logger in the visitor's console and nowhere useful;
`lib/logger.test.ts` asserts that boundary rather than trusting it. Nothing that
could carry personal data is logged — no request body, no contact-form payload,
no comment body — only identifiers and failure reasons.

`LOG_LEVEL` selects the verbosity, defaulting to `info`:

```bash
LOG_LEVEL=debug npm run dev                     # locally
docker compose up -d          # LOG_LEVEL is passed through by docker-compose.yaml
```

## Tests

Tests run under Vitest with jsdom and React Testing Library. Test files are
**colocated next to the source they cover** and named `*.test.ts` / `*.test.tsx`
— for example `lib/api/client.test.ts` and
`components/home/contact-form.test.tsx`. There is no separate test tree; this
convention is binding on the whole application.

## Standards waiver boundary

The repository's JavaScript standards assume a Vue 3 / Quasar SPA. This
application is a Next.js React app, so a bounded waiver applies to `web/` only:

- **Waived for `web/`**: `[JS-002]`, `[JS-003]`, `[JS-004]`, `[JS-007]`.
- **Still in force**: `[JS-001]`, `[JS-005]`, `[JS-006]`, `[JS-008]`–`[JS-014]`,
  all `[JS-DOCKER-*]` and `[DOCKER-*]`, `[GEN-*]`, `[MAKE-001]`.
- The `[JS-008]` deviation, stated as it is actually practised:
  - **Kebab-case filenames throughout `web/components/**`** (feature components,
    `components/ui/**` primitives and their colocated tests alike). The
    `components/ui` layer is generated by the shadcn/ui CLI, which writes
    kebab-case names and re-writes them on every `npx shadcn add`; holding the
    feature components to a different convention than the primitives beside
    them would make the tree harder to read than the deviation itself.
  - **Kebab-case for App Router reserved segment files** (`page.tsx`,
    `layout.tsx`, `not-found.tsx`, `error.tsx`, `route.ts`). Next.js resolves
    routes by exact filename, so these names are not ours to choose.
  - **PascalCase identifiers for React component functions** (`SectionHeading`,
    `BlogIndex`). JSX treats a lowercase tag as an HTML element, so a
    camelCase component function cannot be rendered as a component at all.
  - Everything else is camelCase, including modules under `lib/` (`siteConfig.ts`,
    `logger.ts`) and every non-component function.
